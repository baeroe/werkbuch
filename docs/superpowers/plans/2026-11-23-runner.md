# Runner und GitHub-Integration: Implementation Plan (Epic)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. In diesem Repo läuft jeder Task als Ticket im Flow des Skills `skilltri:do-ticket` (Umsetzungs-Subagent, getrennter Review-Subagent, Nachweis in „Lösung“, CI grün, Merge, Done, Session-Log).

**Goal:** Ein Item, das einem Bot zugewiesen ist, wird von einem Runner auf Rafaels Mac abgearbeitet (PR, CI, unabhängiges Review, Korrektur, Konflikt, Merge durch werkbuch), PRs aller Personen werden verknüpft und reviewt, und der Runner lässt sich per `curl` aus werkbuch installieren.

**Architecture:** werkbuch (Laravel) führt Runner, Agenten-Konfiguration, Aufträge (`agent_runs`) und Stränge (`agent_threads`) und entscheidet den Ablauf als Zustandsmaschine aus Item-Events und GitHub-Webhooks. Der Runner (`runner/`, Go) pollt `/api/runner/*`, startet Claude Code bzw. Codex headless in einem Worktree je Strang und meldet Ereignisse und Ergebnis; der Agent arbeitet über MCP mit einem kurzlebigen Bot-Token. Zwei GitHub-Apps je Instanz: die Agenten-App (Push, PR, Merge, Webhooks) und die Review-App (Freigabe); das Ruleset bleibt ohne Bypass.

**Tech Stack:** wie `CLAUDE.md` (Laravel 13, React 19, Tiptap, Reverb, Pest, Vitest, Playwright); neu Go (Version wie tussh/skilltri, `go 1.26`) mit Bubble Tea, Bubbles, Lip Gloss, `zalando/go-keyring`, `gopkg.in/yaml.v3`; GitHub-API über Laravels `Http` (keine Bibliothek, Builder darf eine prüfen), JWT der App mit `firebase/php-jwt` oder `lcobucci/jwt` (Builder prüft, was schon im Lockfile liegt).

**Spec:** `docs/superpowers/specs/2026-11-23-runner-design.md` (bindend; Abschnittsnummern unten verweisen darauf). Dazu `CLAUDE.md`, `prototypes/clickdummy/DESIGN.md` (Gestaltung, bindend), `docs/superpowers/specs/2026-10-28-werkbuch-design.md`, der do-ticket-Skill (Vorlage der Prompts).

## Wie dieser Plan ausgeführt wird

- Der Plan ist das Epic **„Runner und GitHub-Integration“** im werkbuch-Projekt `WEBU`; jeder Task unten ist ein Kind (Typ Task, Assignee Rafael), in dieser Reihenfolge nach Rang. Dazu ein Task **„Release“** außerhalb des Epics, den das Epic per Relation `blocks` blockiert; ihn macht nur Rafael.
- **Task 1 (Klickdummy) zuerst, dann Halt:** nach dem Merge von Task 1 geht nichts weiter, bis Rafael die UI im Klickdummy freigegeben hat. Seine Korrekturen kommen als Folge-Runde in Task 1 (eigener PR) oder als neue Tickets; die Tasks 9 bis 11 ziehen ihre UI aus dem freigegebenen Stand.
- Je Ticket ein Umsetzungs-Subagent im eigenen Worktree (do-ticket), danach ein frischer Review-Subagent; Merge erst bei grüner CI (alle Checks).
- Bei großen Tickets (4, 7, 8, 9) schreibt der Umsetzungs-Subagent zuerst seinen Ticket-Plan nach superpowers:writing-plans in den PR (`docs/superpowers/plans/2026-11-23-runner-t<N>-<name>.md`) und arbeitet ihn TDD ab.
- Entscheidungen, die weder Spec noch Plan festlegen: Rulings ab **A472** in `docs/superpowers/plans/2026-10-30-werkbuch-app-rulings.md`; Fachliches zusätzlich als „Änderungen vom …“ in die Haupt-Spec.
- `CLAUDE.md` pflegt jedes Ticket im selben PR (Abschnitte wie bisher: Architektur, Fallstricke, Kommandos).

## Global Constraints

- Alle Regeln aus `CLAUDE.md` gelten: Actions und Domain, Events nur in Transaktionen, Sichtbarkeit nur über `Visibility`, 100 % Zeilen PHP und Frontend, Larastan 8, Pint, `tsc`, Rechte- und Routen-Matrix, OpenAPI-Vertrag, MCP-Parität (A397), Tastatur-Manifest, axe, Doku in `docs/en` und `docs/de`, Texte über `lang/*.json`.
- Runner-Protokoll unter `/api/runner/*`, nicht unter `/api/v1` (Spec 6.1); GitHub-Webhooks unter `POST /github/webhook` (11.4).
- Runner-Version = `config('werkbuch.version')`, kein eigener Tag (3).
- Kein Geheimnis (Runner-Token, Run-Token, Installations-Token, Private Keys, Webhook-Secrets) in Events, Jobs, Logs, Auftragsprotokollen oder Antworten außer der einen, die es ausgibt; Tests suchen danach wie bei den Webhooks.
- Der Agent mergt nie und setzt keinen Status; das sperren werkbuch (Run-Token, 11.2) und GitHub (Ruleset ohne Bypass, 11.3) hart.
- Statuswechsel und Zuweisungen des Ablaufs nur mit `Actor::agent($bot)`; Ereignisse mit diesem Actor lösen nie einen Auftrag aus (7.1, 7.2).
- Go: `go vet`, `go test -race ./...` grün; CI-Job `runner` (nie `tests`), Actions per SHA, fester Runner (`WorkflowsTest`).
- Code, Kommentare, Commits Englisch; Arbeitsdokumente Deutsch.

## Review Focus

- **Zwei Runner holen gleichzeitig ab, oder ein Lease läuft ab, während das CLI noch arbeitet:** nie zwei Läufe desselben Auftrags; ein verspäteter Heartbeat oder ein Ergebnis eines ersetzten Versuchs wird abgelehnt (Versuchsnummer). → Task 3.
- **Webhooks doppelt, verspätet oder in falscher Reihenfolge** (Check-Suite eines alten Commits nach neuem Push, Redelivery): CI-Zustand und Merge gelten nur für den aktuellen Head-Commit, jede Delivery wirkt einmal. → Tasks 7 und 9.
- **Push während eines laufenden Reviews:** ein `approve` für Commit A gibt nie Commit B frei; das laufende Review wird abgebrochen. → Task 9.
- **Prompt-Injection in Item, Kommentar oder PR-Text:** der Agent versucht Status, Zuweisung, Merge, Push auf den Standard-Branch: werkbuch lehnt mit Run-Token ab (403 `agent_forbidden`), GitHub lehnt ohne Freigabe ab. → Tasks 3 und 7.
- **Mac schläft oder verliert das Netz mitten im Lauf:** Auftrag `lost` nach Lease, einmal neu eingereiht, Worktree und Session wiederverwendbar oder sauber neu; kein doppelter Push, keine verwaisten Run-Tokens. → Tasks 3 und 4.

- Run-Tokens: `App\Support\RunTokens::issue(AgentRun $run): string`, `revoke(AgentRun $run): void`; Kennzeichnung am Token (Spalte `agent_run_id` an `personal_access_tokens`)
- Harte Sperre: `App\Access\RunTokenGuard::refuse(Actor $actor, string $what): void` (403 `agent_forbidden`), gerufen in den Actions aus Spec 11.2
- REST `/api/v1`: Runner lesen/umbenennen/widerrufen, Aufträge lesen (je Item, je Runner), abbrechen, erneut starten, Agenten-Konfiguration; MCP-Aktionen nach A397 (Pairing-Code nur Sitzung)
- Tests: `tests/Feature/Runners/*`, `tests/Feature/AgentRuns/*`, `tests/Integration/ClaimRaceTest.php`, Rechte-Matrix mit Spalte „Run-Token“

**Interfaces (Produces):**
- `ClaimRun::handle(Runner $runner, array $capacity): ?array` → Antwort aus Spec 6.3 (ohne GitHub-Token, das ergänzt Task 7)
- `AgentRun::STATUSES` = `queued, waiting, running, canceling, succeeded, failed, canceled, timed_out, lost`; `AgentRun::TYPES` = `task, correction, conflict, review, comment`
- `EnqueueRun::handle(Actor $actor, User $bot, WorkItem $item, string $type, ?AgentThread $thread, array $context = []): AgentRun` (von Task 8 benutzt)
- Protokoll-Header `X-Werkbuch-Runner-Version`, `X-Werkbuch-Protocol` (Zahl, Start `1`)

**Tests (Auszug, Namen verbindlich):**
- `it hands a run to exactly one of two runners claiming at once` (zwei Verbindungen)
- `it refuses a heartbeat or result of a replaced attempt`
- `it marks a run lost after its lease and queues it once more, then fails it`
- `it refuses state changes, assignment, archive and delete through a run token with agent_forbidden` (je Action aus 11.2)
- `it revokes the run token when the run ends in any status`
- `it never writes a runner, run or installation token into events, jobs or the log`
- `it claims only runs within the free places set in werkbuch` (gesamt, je Repo, leicht) und `it sends the places and stores the last load with every claim and heartbeat`
- `it orders corrections and reviews before tasks, then priority, then age`
- `it hands a correction or comment of an open thread to the runner of the thread, waits while it is offline and moves the thread after the grace period`
- `it prunes run events after 30 days and keeps at most 2000 events or 1 MB per run`

**Abnahme:** Protokoll mit `curl` gegen DDEV durchspielbar (Pairing, Claim, Heartbeat, Events, Ergebnis, Abbruch), Nachweis mit der Ausgabe.
