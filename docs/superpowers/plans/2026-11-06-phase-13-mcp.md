# Phase 13: MCP – Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** werkbuch bekommt einen MCP-Server unter `/mcp` (Spec 6.2): Streamable HTTP mit Bearer-Token (Fähigkeit `mcp`), je Ressource ein Lese-Tool `<ressource>` (`IsReadOnly`, braucht `read`) und ein Schreib-Tool `manage-<ressource>` (`IsDestructive`, braucht `write`) mit `action`-Parameter, dazu `whoami`, `search` und `get-upload-url`, drei Referenzen als MCP-Resources und Server-Instructions. Die Tools sind dünne Hüllen um dieselben Actions, `ListSpec`s, Resources und Schemas wie REST; Fehler kommen als Problem mit `reason`. Abnahme: `McpFlowTest` fährt einen echten MCP-Ablauf (`server/discover` im aktuellen Protokoll, `tools/list`, `tools/call`) gegen die Route und deckt Erfolgskriterium 2 und 4 und das Agent-Szenario aus 6.2 ab; `McpRouteTest` belegt daneben den alten Handshake über `initialize`.

**Architecture:** laravel/mcp (1.1.1) stellt Transport, JSON-RPC und Registrierung; `routes/ai.php` hängt `WerkbuchServer` an `/mcp`, und zwar **in einer Middleware-Gruppe vor der Route** (Drossel `mcp` über `RateKey`, Sprache, `auth:sanctum`, aktives Konto, Token mit `mcp`), damit Drossel und Anmeldung vor der Middleware des Pakets laufen. Jedes Tool erbt von `App\Mcp\Support\ReadTool` bzw. `WriteTool` und beschreibt seine Aktionen als `McpAction` (Name, Argumente, `input` = Body der REST-Operation, REST-Zwilling, Closure, die eine Action ruft). Die Argumente kommen aus dem schon von `TrimStrings`/`ConvertEmptyStringsToNull` geputzten JSON der HTTP-Anfrage (A149), Query-Argumente in der Form der REST-Query (Listen als Komma-Text); die Schemas der Argumente aus denselben `App\OpenApi`-Methoden und `ListSpec`s wie das OpenAPI-Dokument (Komponenten je Tool einmal unter `$defs`), das Ergebnis ist der Body der REST-Antwort (ohne `links`, Rich Text nur als Markdown, leere Objekte bleiben Objekte). Tests prüfen das gegen REST: gleiche Antwort bei jedem Lesen (Parität), gleiche Schemas wie das Dokument, je Aktion dieselbe Fähigkeit wie die Route ihres Zwillings, jede Aktion genau eine Zeile in der Tool-Matrix, ein festes Budget für die Größe von `tools/list`.

**Tech Stack:** wie Phase 12; neu `laravel/mcp` (zieht `illuminate/json-schema` nach, siehe „Paketversionen“).

**Spec:** `docs/superpowers/specs/2026-10-28-werkbuch-design.md` (1 Erfolgskriterien 2 (per MCP), 4 („… und das MCP-Tool“), 8 (Doku MCP); 2 Anti-Ziele „API und MCP hinken hinterher“, „Datenlecks“, „Doppelte Logik“; 3 Zeilen „MCP“, „Auth“; 4.2 Tokens (`read`, `write`, `mcp`); 4.16 Markdown in REST und MCP, Anhänge; **6.2 komplett**; 7.2 Actions, 7.5 Datenlecks; 9 „MCP (Namen, Annotationen, Doku)“; 10 Doku „MCP mit allen Tools und Einrichtung“; „Änderungen vom …“ zu 6.1/6.2 aus den Phasen 4–12), Master-Plan `docs/superpowers/plans/2026-10-30-werkbuch-app.md` (Global Constraints, Verträge „Actor“, „Fehler“, „Resources“, „Routen“, Phase 13), Rulings `docs/superpowers/plans/2026-10-30-werkbuch-app-rulings.md` (A75, A96, A149, A151, A174, A179, A203, A206, A229, A232, A235, A261, A305, A363, A364, A369, A375, A384–A395; „Für spätere Phasen vorgemerkt“, Zeile Phase 13 → Tasks 3a, 4, 7b–11), Phase-12-Plan `docs/superpowers/plans/2026-11-06-phase-12-rest-openapi.md` (Form, Gates), `routes/api.php`, `tests/Feature/Api/routes.php`, `tests/Feature/Access/matrix.php`, `app/OpenApi/*`, `resources/js/features/settings/tokens/snippets.ts`. ## Review Focus

- **Rechte an REST vorbei:** ein Token mit `read`+`mcp` ruft `manage-work-items`, ein Token nur mit `mcp` ruft `work-items`, ein Token ohne `mcp` spricht `/mcp` an, die Sitzung der Oberfläche spricht `/mcp` an (echtes Cookie bzw. ein Guard, der die Person schon kennt), ein deaktiviertes Konto benutzt ein altes Token. Erwartet: das Tool fehlt in `tools/list` und ist beim Aufruf unbekannt (JSON-RPC `-32602`), ohne `mcp` 403 `forbidden`, Sitzungs-Cookie 401 `unauthenticated` (ohne `web`-Gruppe kein Cookie), schon bekannter Guard 403 `token_required`, deaktiviert 401; ein `TransientToken` sieht kein Tool. → Task 1 (`McpRouteTest`), Task 3a (`McpServerTest`), Task 3b (`McpToolMatrixTest` über alle Zeilen von `tools.php`, Fähigkeit je Zwilling).
- **Tür vor dem Paket:** eine Flut mit falschem `Mcp-Method`-Header oder fremdem `Origin` zählt in der Drossel und kommt nie bis zum Dekodieren des Bodys durch das Paket ohne Anmeldung. → Task 1 (`McpRouteTest`).
- **Unicode-Leerraum und Rich Text (A149):** ein Titel aus nur einem geschützten Leerzeichen über MCP ist 422 wie über REST; ein Textknoten `" "` zwischen zwei Marken in `description_json` bleibt erhalten; ein leerer String wird `null`; Listen-Filter kommen in der Komma-Form der Query an. → Task 3a (`McpArgumentsTest`).
- **Upload-URL missbraucht:** eine abgelaufene URL (15 min + 1 s), eine, deren Token vor ihr abläuft, eine mit geändertem `project_id`/`kind`/`work_item_id`, eine nach dem Widerruf des Tokens oder dem Deaktivieren des Kontos, eine für ein Item, das der Token nicht ändern darf, eine Datei über `ATTACHMENTS_MAX_MB`, mehr als 60 Uploads je Minute über REST und URL zusammen. Erwartet: 403 bzw. 401 bzw. 413 bzw. 429 als Problem, keine Zeile in `attachments`, keine Datei. → Task 8a (`McpUploadTest`).
- **Interna und Geheimnisse in Fehlern:** eine Ausnahme ohne `Problem` in einem Tool wird gemeldet (`report`) und kommt als `server_error` ohne Meldung (außer `app.debug`), eine `ModelNotFoundException` als 404 wie über REST; das Webhook-Geheimnis taucht in keinem Fehlertext, keinem Log (`MessageLogged`), keinem Event und keiner Zeile von `jobs` auf; Texte in Ergebnissen sind Daten, die Instructions sagen es. → Task 3a (`McpProblemTest`), Task 10 (`WebhookToolsTest`), Task 11 (`McpServerTest` Instructions).
- **Datenleck über MCP:** ein Außenstehender eines privaten Projekts bekommt über `search` (auch per Key-Sprung), `work-items:get|list|query`, `views:items`, `relations:list`, `comments:list`, `pages:tree`, `attachments:get` und `get-upload-url` nichts davon (404 bzw. leer bzw. `hidden`), genau wie über REST. → Task 12 (`McpLeakTest`).

## Werkzeugschnitt

## Vorschläge für neue Rulings (ab A396; A393–A395 sind in Phase 12 vergeben)

- **A396 · laravel/mcp genau 1.1.1,** zustandslos über Streamable HTTP (`POST /mcp`, `GET`/`DELETE` 405, keine Sitzung des Protokolls, keine Server-Benachrichtigungen); Protokolle `2026-07-28` über `server/discover` und `2025-11-25`, `2025-06-18`, `2025-03-26` über `initialize` (ältere bekommen `2025-11-25`). *Grund:* das Paket der Spec; 1.1.2 ist jünger als zwei Wochen (Regel der Planung), und ein zustandsloser Server braucht keinen Speicher je Client. *Falls falsch:* auf 1.1.2 bzw. die nächste 1.x heben, sobald sie zwei Wochen alt ist (Tests `McpRouteTest`, `McpServerTest` belegen das Update).
- **A397 · Werkzeugschnitt:** 30 Tools nach der Tabelle „Werkzeugschnitt“; Organisation und die sechs Kataloge sind **ein** Paar `organization`/`manage-organization` mit `get`/`update` und Aktionen je Katalog (Spec 6.2 nennt sie als eine Ressource „Organisation und Einstellungen“), Favoriten stehen bei den Projekten, Tokens (Liste, Widerruf) und `mentionable` bei den Personen; `attachments`/`manage-attachments` folgen aus Spec 4.16 (Datei lesen, Datei aus der Liste nehmen), obwohl 6.2 sie nicht nennt; nicht über MCP gehen, was nur die Sitzung darf (Tokens anlegen, Passwort, zweiter Faktor), die System-Seite und `GET /references`. *Grund:* die Zahl der Tools bleibt überschaubar und folgt den Ressourcen von 6.2; jede Aktion hat einen REST-Zwilling; was ein Agent nicht braucht oder nicht darf, bleibt draußen. *Falls falsch:* Organisation und Kataloge getrennt bzw. je Katalog ein eigenes Paar (das Budget von `tools/list` entscheidet mit); System als `system`/`manage-system` für Org-Admins.
- **A398 · Argumente:** `action`, die Platzhalter der REST-Route in snake_case, bei `GET`-Zwillingen deren Query (`filter` als Objekt, Listen im Schema als Arrays, an die Action in der Form der REST-Query als Komma-Text, `McpArguments::query()`), bei Bodies ein Argument `input` = der Body des Zwillings mit demselben Schema (aus denselben `App\OpenApi`-Methoden, Komponenten unter `$defs`, `McpSchemasTest`); die Argumente kommen aus dem JSON der HTTP-Anfrage **nach** `TrimStrings` und `ConvertEmptyStringsToNull` (mit `RichTextInput::RAW_KEYS`), damit MCP Unicode-Leerraum trimmt wie REST (A149 erledigt, ohne zweite Regel). Ein Body ohne JSON-`Content-Type` ist 415 (`GuardMcpRequest`; nur JSON wird geputzt). *Grund:* keine zweite Liste von Feldern; REST-Doku und MCP-Doku beschreiben dieselben Bodies; `ListQuery` und die Kurzform nehmen nur Text oder Zahl. *Falls falsch:* flache Argumente je Aktion (Vereinigung aller Body-Schlüssel).
- **A399 · Ergebnis:** der Body der REST-Antwort ohne `links`, Rich Text nur als Markdown (die `_json`-Formen fallen weg, Rich-Text-Werte in `values` werden ihr Markdown), über REST leere Antworten `{done: true}`; leere Objekte bleiben Objekte; `meta.path` ist der Pfad des Zwillings. MCP-Standards: `per_page` 25, `lean` an, wo es `lean` gibt (`work-items:list|query`, `views:items`, `templates:list`); ausdrücklich gesetzt wie REST. *Grund:* Spec 6.2 „dieselben Darstellungen wie REST, Rich Text als Markdown“; Parität ist so per Test prüfbar (`McpParityTest` setzt `per_page` und `lean` ausdrücklich); 100 volle Items als `structuredContent` und gespiegelter Text sprengen den Kontext eines Agenten (Claude Code warnt ab rund 25.000 Tokens je Aufruf). *Falls falsch:* beide Formen ausgeben bzw. die Standards von REST übernehmen.
- **A400 · Fehler eines Tools** sind ein Ergebnis mit `isError: true`, einer Textzeile `"<status> <reason>: <satz>"` samt Feldfehlern und `structuredContent` = Problem wie REST (Sprache des Kontos), gebaut über Laravels `ExceptionHandler` (`report` mit `dontReport`, `render` wie REST, also auch `ModelNotFoundException` → 404); eine Ausnahme ohne Problem wird gemeldet und kommt ohne Meldung; Fehler vor dem Tool (Auth, Drossel, Größe, Origin) bleiben HTTP-Status mit Problem; ein Tool, das das Token nicht darf, ist JSON-RPC `-32602` („nicht gefunden“). *Grund:* Spec 6.2 „lesbarer Text“, Vertrag „Fehler“ (MCP macht daraus Text) und dieselben `reason`s wie REST. *Falls falsch:* nur Text, ohne `structuredContent`.
- **A401 · Nur Tokens an `/mcp`:** ein `PersonalAccessToken` braucht `mcp`, Lese-Tools zusätzlich `read`, Schreib-Tools `write`; Resources nur `mcp`; geprüft wird immer `instanceof PersonalAccessToken && can()`, nie `tokenCan()`. *Grund:* Spec 6.2 „Bearer-Token“; ein Browser-Tab soll keinen MCP-Client spielen (CSRF gibt es dort nicht). Im Betrieb kommt eine Sitzung nicht über die Anmeldung hinaus (401: `routes/ai.php` hat keine Gruppe `web`, also kein Cookie); `token_required` (403) greift, wenn ein Guard die Person schon kennt, und dann hätte sie ein `TransientToken`, dessen `can()` alles erlaubt. *Falls falsch:* die Sitzung zulassen.
- **A402 · Drossel `mcp`:** `MCP_RATE_LIMIT` (Standard 300/min) je gültigem Token, sonst je Adresse (`RateKey::for`), ein Kontingent neben dem der API, in einer Gruppe vor der Middleware des Pakets (eine Flut falscher Header zählt); Ping und „erneut senden“ zählen dazu in `webhook-send` je Konto im selben Zähler wie REST (`RouteThrottle`), Uploads über die URL in `attachments` je Konto wie REST. *Grund:* Spec 6.2 „300/min je Token“, A387; über MCP darf ein Konto nicht doppelt so oft pingen oder hochladen wie über REST. *Falls falsch:* ein gemeinsames Kontingent für API und MCP je Token.
- **A403 · Upload-URL:** `get-upload-url` stellt eine signierte URL `POST /api/mcp/uploads/{token}` aus (`project_id`, `kind`, `work_item_id` in der Signatur), die mehrfach benutzt werden darf; beim Hochladen gilt das Token noch einmal (`PersonalAccessToken`, nicht widerrufen, nicht abgelaufen, Konto aktiv, `write` und `mcp`), die Rechte prüft `UploadAttachment` erneut; ein Upload ohne Besitzer gehört niemandem wie aus dem Editor (A232). Ergänzungen: (1) der Guard `sanctum` wird per `Auth::shouldUse` Standard, bevor er die Person bekommt; (2) Fehler kommen in der Sprache des Kontos (`App::setLocale` nach der Anmeldung; ein 403 von `signed` bleibt in der Sprache der Organisation); (3) die URL gilt `min(15 Minuten, Ablauf des Tokens)`; (4) Uploads zählen im Kontingent `attachments` je Konto wie über REST (`RateKey::account` liest das Token der URL). *Grund:* Spec 4.16, 6.2 (wie prevju: Binärdaten nie in Tool-Argumenten); ohne Zustand in der Datenbank; eine URL nur für einen Upload brächte nichts, weil `curl` nach einem Abbruch mit derselben URL neu ansetzen muss, und die Drossel begrenzt den Schaden. *Falls falsch:* eine URL nur für einen Upload (eigene Tabelle mit Verbrauch).
- **A404 · `types` ohne Art ist 422** (`field.types.empty`, REST und MCP); weggelassen oder `null` heißt weiter „alle Arten“ (T9-M2). *Grund:* „keine Art“ als „alle“ zu lesen überrascht einen Agenten, der eine leere Liste baut. *Falls falsch:* leere Liste = leere Antwort.
- **A405 · Suchfilter für Items:** `type_id`, `state_category`, `assignee_id` und `label_id` engen die Item-Treffer von `GET /search` und `search` ein, über die schon indexierten Felder (A206), vor `limit`; die Werte werden vor der Engine geprüft (ULIDs, Kategorien); `assignee_id` `none` geht nur allein (Scout verknüpft Felder mit UND, „niemand oder X“ geht nicht); der Key-Sprung gilt nur, wenn das Item alle gesetzten Filter erfüllt. *Grund:* Vormerkung Phase 6; ein Agent sucht gezielt; ein Key-Treffer, der den Filter verletzt, wäre ein falscher Treffer. *Falls falsch:* gefilterte Suche nur über `work-items:list` mit `filter.q`.
- **A406 · Leer-Marke für `created_at`/`updated_at` in `ItemOrder`** (T5-M1). *Grund:* beide Spalten dürfen `null` sein; ohne Marke stünden solche Items je nach Richtung vorn. *Falls falsch:* die Spalten NOT NULL machen.
- **A407 · Tools öffnen keine Transaktion** (`ArchTest`), Löschungen über MCP laufen darum auf Ebene 0 und `ReadCommitted::run` greift (A261, Vormerkung Phase 7; `McpReadCommittedTest`). *Grund:* sonst kehrte der Race aus T13-M8 zurück. *Falls falsch:* eine Mehrfachaktion über MCP setzt READ COMMITTED selbst.
- **A408 · Frühere Keys über MCP** lösen ohne Umleitung auf; das Ergebnis trägt den aktuellen Key, ein unsichtbares Item ist 404 wie ein unbekanntes. *Grund:* MCP kennt kein 301; REST leitet nur für Sichtbares um (Phase 4). *Falls falsch:* ein Hinweis `former_key` im Ergebnis.
- **A409 · Referenzen** sind die Abschnitte zwischen `<!-- reference:start -->`/`<!-- reference:end -->` der englischen Seiten `concepts/views.md`, `concepts/rich-text.md`, `concepts/types-and-properties.md`, zur Laufzeit gelesen, als `werkbuch://reference/{filters,markdown,field-types}`; fehlt eine Seite oder Marke, ist das JSON-RPC `-32603` mit `reference_missing` und ein Bericht. *Grund:* Spec 6.2 „aus der englischen Doku gelesen“; Marken statt Überschriften überstehen Umformulierungen; `ReadResource` kennt kein Ergebnis mit `isError`. *Falls falsch:* eigene Referenz-Seiten unter `docs/en/reference/`.
- **A410 · `counts` über MCP unterscheidet Objekt und Liste wie REST** (K17 der Phase 12): die Form von `input.filters` liest `work-items:counts` aus dem rohen Body (`instanceof stdClass`), die Werte aus der geputzten Tasche; ein Objekt (auch `{"0": …}`) geht als Objekt an `CountWorkItems`, eine Liste ist 422 `field.filters.invalid` wie über REST. *Grund:* JSON-Argumente kommen als PHP-Arrays an, `{"0": …}` und `[…]` sehen dort gleich aus; der rohe Body kennt den Unterschied, und so antwortet MCP wie REST. *Falls falsch:* eine Liste als Objekt mit Schlüsseln `0…` lesen.
